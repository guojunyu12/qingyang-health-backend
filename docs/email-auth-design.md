# M01 邮箱验证码注册登录设计

## 已确认目标

注册和登录统一使用邮箱验证码，不再要求手机号。新邮箱验证成功自动注册，已有邮箱验证成功直接登录。使用现有163邮箱通过 SMTP TLS 发送验证码。补齐当前不存在的登录页面，并在本地 MySQL 8.4 建立对应结构、验证真实闭环。此阶段只交付 M01 认证切片，不实施上传或通知业务。

## 实现选择

推荐按团队总契约增加 NestJS 后端 `server/`，前端通过同站 `/api/v1` 代理访问，保持后续 M02–M06 模块装配入口。相比直接把认证写入 Next.js Route Handler，多一个本地 API 进程，但避免后续再迁移认证；不采用外部认证平台，以沿用统一 MySQL 用户与事务。

前端保持 Next.js + React + TypeScript。后端使用 mysql2/promise 单连接池，SMTP 使用 Nodemailer，Redis 提供邮箱/IP限流。具体依赖版本在实施时锁定。后端显式加载 `.env.m01.local`；秘密不进入 NEXT_PUBLIC_ 或接口响应。

## 页面与交互

新增 `/login`，浅紫风格，提供邮箱输入、发送验证码、6位验证码、倒计时、登录提交、发送/提交中状态和可访问错误提示。发送失败保留邮箱，验证码错误保留表单；更换邮箱后清除旧 challenge。重复点击发送与提交均禁用。登录界面说明“未注册邮箱验证后自动创建账号”。

登录成功跳转至受约束的本站业务路径，默认 `/dashboard`；禁止外部 returnTo。增加独立 AccountSummary 组件，提供真实昵称、脱敏邮箱及退出入口；由“我的”页面引用，不重写M05业务。未登录访问业务页面进入登录页。业务页面目前仍为演示数据，必须保留演示标记；登录不意味着健康记录后端已经接入。账号切换和退出清理现有本地演示状态，避免混淆跨账号数据。

## 接口

基础路径 `/api/v1`，统一 data/error/meta 包装，不返回验证码或长期凭据。

- `POST /auth/email-codes`：email、purpose=login，返回 challengeId、expiresInSeconds=300、resendAfterSeconds=60。
- `POST /auth/login`：challengeId、6位code、deviceId、platform=h5。原子消费挑战，创建或查询用户，建立会话；H5设置HttpOnly Cookie。
- `GET /me`：返回真实账号摘要，不返回密文、摘要或验证码。连续签到等M05字段在其端口未接入时明确不提供推断值。
- `GET /auth/csrf`：返回绑定当前会话的 CSRF token。
- `POST /auth/refresh`：轮换刷新凭据；旧凭据重放撤销对应会话。
- `POST /auth/logout`：撤销当前会话并清Cookie，204。

客户端统一请求器实现 credentials、错误解析和401刷新单飞；禁止在localStorage存刷新凭据。写请求校验Origin和会话CSRF，认证前发送/登录校验同站来源。只支持本期H5，不把App令牌流程报为完成。

## 数据库与迁移

已执行 V001 的SHA保持不变。新增 M01 变更提案及 V002 增量迁移，维护版本记录和执行校验，禁止重复执行或以reset处理错误。

将 users 和 auth_challenges 中手机号密文/查找摘要迁移为邮箱密文/查找摘要，更新相关约束与索引，邮箱摘要唯一。现有本地库尚无账号；迁移仍须先检查旧手机号账号，若存在不能自动猜邮箱，停止并报告人工迁移需求。邮箱 trim、ASCII小写后校验格式，首版接受常规ASCII邮箱，不去点或剥离加号，避免误合并不同地址。邮箱使用 AES-GCM 加密，查找使用服务端密钥HMAC，密钥独立于SMTP授权码。验证码只存绑定challenge的带密钥摘要。

复用 user_sessions、refresh_tokens、user_roles。新账号默认普通角色，不生成健康目标、演示历史或初始积分。M05尚未交付 PointsPort 时，认证采用明确的模块端口边界；零余额开户由M05实现，不由M01越权写积分表。独立认证验收与包含积分开户的全模块验收分别报告，缺少真实PointsPort不得宣称团队整合完成。

## 安全与失败恢复

验证码5分钟有效、同邮箱60秒重发、最多5次错误尝试，按邮箱与IP进行限流。所有验证以服务端时间为准；错误次数必须提交，不能随错误抛出回滚。同一挑战并发提交最多消费一次。发送新验证码使同邮箱旧的未消费挑战失效；SMTP调用不在数据库事务中等待，发送失败的挑战不可登录。限制单邮箱和单IP小时发送额度，Redis不可用时拒绝发送，不退化成无限制。

Cookie在生产使用Secure/HttpOnly/SameSite=Lax，本地HTTP仅开发模式允许非Secure。访问会话短期有效，刷新凭据随机生成并只保存摘要。刷新在事务中锁定会话/令牌并轮换，重放撤销该会话；不把token或Cookie写入普通幂等缓存与日志。退出操作清理用户缓存与Cookie。

SMTP使用 smtp.163.com:465 并验证TLS证书。当前已验证SMTP认证；真实验证码发送只发送到用户在登录页面明确提交的邮箱。不提供任意邮件标题/内容接口，错误日志不暴露授权码、验证码、Cookie或完整邮箱。

## 验收

1. 新邮箱收到验证码后完成自动注册；已有邮箱登录复用同一用户。
2. 错码计数真实增加，过期/耗尽/已消费/被替换挑战不能登录。
3. 并发提交同一验证码仅一次成功，SMTP失败不能登录，重发限流有效。
4. 页面刷新恢复账号、并发401刷新单飞、刷新重放撤销及退出后不可继续访问。
5. 两个账号身份隔离，未登录请求401，非法Origin或CSRF拒绝。
6. 新库V001→V002与既有本地V001→V002均通过；基线SHA未变，无手机号新注册入口。
7. typecheck、构建、认证集成测试、移动端登录页面浏览器测试通过；真实SMTP发送结果与自动测试分开记录。
8. 更新M01认证接口片段、迁移说明和交付单，标明M05开户与其他业务尚未整合。
