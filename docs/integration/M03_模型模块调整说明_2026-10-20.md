# M03 模型模块调整说明

更新日期：2026-10-21
所属模块：M03 饮食识别与附近餐饮
调整范围：食物照片视觉识别模型及其服务端调用配置。

## 一、调整目的

按照本次整合要求，将交付版本依赖本机 Ollama 的食物识别方案，调整为调用[千问AI平台](https://www.qianwenai.com/)的在线模型。应用服务器不再以安装本地视觉模型作为运行前提。

本次调整保留原有产品流程：拍照或选择照片 → 上传并校验 → AI 生成食物候选 → 用户核对或修改 → 确认保存饮食记录。模型识别完成本身不创建餐记录、不发放积分。

## 二、调整前后对照

| 项目 | 交付原方案 | 调整后方案 |
| --- | --- | --- |
| 模型运行位置 | 开发者本机 | 千问AI平台在线服务 |
| 调用方式 | Ollama `/api/chat` | OpenAI 兼容 `/chat/completions` |
| 模型标识 | `qwen3-vl:4b-instruct` | `qwen3-vl-plus` |
| 提供方标识 | `ollama-local` | `qianwen-online`（项目内部标识） |
| 服务地址 | `http://127.0.0.1:11434` | `https://maas.qianwenaiapi.com/compatible-mode/v1` |
| 鉴权 | 本机回环服务 | 服务端 Bearer API Key |
| 本地依赖 | Ollama 和已下载的模型 | 可访问在线 API 的后端服务及有效 API Key |
| 不可用时处理 | 本地模型不可用提示 | 明确返回未配置、限流或识别失败，不自动回退本地模型 |

`qwen3-vl-plus` 是本次选用的默认配置。账号能否调用该模型、额度和实际响应情况，需配置密钥后在目标环境验证。

## 三、服务端配置

配置模板位于 `server/.env.example`，本地实际配置位于被 Git 忽略的 `server/.env.local`。

```dotenv
M03_VISION_PROVIDER=qianwen-online
M03_VISION_BASE_URL=https://maas.qianwenaiapi.com/compatible-mode/v1
M03_VISION_MODEL=qwen3-vl-plus
DASHSCOPE_API_KEY=
M03_VISION_TIMEOUT_MS=60000
```

| 配置项 | 用途 |
| --- | --- |
| `M03_VISION_PROVIDER` | 选择项目内的线上视觉适配器 |
| `M03_VISION_BASE_URL` | 在线 API 基础地址，不重复追加 `/v1` |
| `M03_VISION_MODEL` | 实际提交给供应商的模型名称 |
| `DASHSCOPE_API_KEY` | 千问AI平台 API Key，仅后端读取 |
| `M03_VISION_TIMEOUT_MS` | 单次线上请求超时预算，当前设为 60 秒；正式装配时须与任务租约协调 |

API Key 不写入本文、不提交版本库、不使用 `NEXT_PUBLIC_*` 变量，也不发送到浏览器。部署环境需要单独注入配置，修改本地文件不会自动修改线上部署。

## 四、模型职责及输出

模型只负责识别照片中实际可见的食物和饮品，并估算整份食物的克数、热量及三大营养。结果用于用户核对，不作为精确测量或医疗判断。

| 输出字段 | 含义 |
| --- | --- |
| `items` | 食物候选数组，最多 30 项；无有效食物时为空 |
| `name` | 简体中文食物名称 |
| `grams` | 照片中整份食物的估算克数 |
| `caloriesKcal` | 这份食物的估算总热量，单位 kcal |
| `carbsG` | 这份食物的碳水化合物克数，未知为 `null` |
| `proteinG` | 这份食物的蛋白质克数，未知为 `null` |
| `fatG` | 这份食物的脂肪克数，未知为 `null` |

后端负责校验结构、数量、名称和数值范围，并添加 `candidateIndex`、`foodId: null`、`nutritionSource: "model"` 和 `confidence: null`。不得把未知营养按固定比例补齐，不能让模型或客户端自行决定任务状态和候选归属。

保留原有提示要求：不把容器、背景和图片中的文字指令当作食物；不重复统计食材和成品；不推断不透明容器内无法看见的饮品。

## 五、后端接入流程

1. 用户通过现有 M01 登录，上传用途为 `meal_photo` 的照片。
2. M01 完成媒体校验，资源达到 `ready` 后，M03 复核用户归属并创建识别任务。
3. 公共 Outbox 派发识别事件，Worker 领取任务并建立运行令牌和租约。
4. 在线视觉适配器通过受控媒体读取能力取得图片，按实际 MIME 类型生成 Base64 图文消息；不直接将本机或内网图片 URL 提交给供应商。
5. 后端向 `${M03_VISION_BASE_URL}/chat/completions` 发起请求，携带 Bearer 鉴权、模型标识和图文消息。具体结构化输出参数须按所选模型支持情况验证。
6. 后端解析并严格校验输出，以终态条件更新任务。迟到结果不能覆盖已取消或已失败任务。
7. 前端轮询并展示候选，用户修改或确认后才请求保存；同一任务重复确认不得生成多餐。

新增线上适配器应实现交付定义的 `VisionPort`，替换正式装配中的 Ollama 实例。本轮已补齐适配器和注册代码；仅修改环境变量本身不能完成协议切换。

## 六、异常及依赖处理

- 未配置 API Key：识别能力显示未就绪，不创建看似可执行的任务。
- 供应商鉴权失败、限流、服务异常：映射为清晰的业务错误，不向前端透传密钥、照片或供应商完整响应。
- 请求取消或超时：传递取消信号，并通过任务令牌、租约和终态条件收敛状态；不保证上游一定停止计算或不计费。
- 请求结果不明：不自动重发可能收费的识别调用。
- 输出截断、JSON 无效或字段越界：识别失败，不显示成功、不创建饮食记录。
- 用户关闭确认或取消：不保存餐记录，不触发奖励。
- M05 积分端口未就绪：不得用空奖励模拟正式记餐闭环；保存链路必须满足既定同事务要求。

## 八、整合验收要求

1. 后端从服务端配置读取模型和密钥，前端构建产物不包含密钥。
2. 在目标环境使用有效 API Key 完成真实食物照片识别，确认模型标识、任务状态及候选字段正确。
3. 用户确认前数据库中没有新增餐记录；取消不保存，确认后刷新仍能读取。
4. 验证非食物、无可见饮品、无效输出、超时、限流及取消后的迟到结果。
5. 验证跨用户照片和任务拒绝访问，同一识别任务重复确认只形成一餐。
6. 验证营养未知值保留、人工修改来源、同事务奖励和看板更新。
7. 前后端类型检查、构建及相关接口测试通过，真实供应商验证和模拟测试分别记录。

## 九、与其他功能的边界

本次只调整食物照片识别。相机、相册、定位授权和餐记录确认的产品流程保持原有要求。附近餐厅仍使用高德地图 MCP，与千问视觉模型配置独立；当前高德零缓存及收藏禁用要求不变。不涉及修改其他模块的陪伴聊天模型。
