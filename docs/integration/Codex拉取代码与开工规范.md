## 3. 工作区保护：先判断，再切分支

| 状态 | 允许操作 | 不得操作 |
| --- | --- | --- |
| 工作区干净 | fetch、比较历史；确认后切换/快进 main | 跳过仓库和历史核对 |
| 有明确属于当前任务且已授权保存的改动 | 在本人任务分支按文件白名单保存，说明修改，再同步 | 为了省事 git add . / git add -A |
| 有其他窗口、归属不明或未授权改动 | 记录文件清单，继续 fetch/只读比较；暂停会覆盖它们的操作，说明具体阻碍 | 自动 commit、stash、reset、clean、checkout/restore 这些文件 |
| 正在 merge/rebase/cherry-pick，或有未解决冲突 | 识别已有操作归属并报告，继续不冲突的只读检查 | 为完成拉取擅自 abort、continue 或重置现场 |
| detached HEAD / 分支被其他 worktree 使用 | 保留现场，记录状态并确定正确开发位置 | 强行抢占分支、删除 worktree |

不要把环境文件、业务资料、旧原型或别人的未提交文档夹带进本次提交。禁止用复制旧目录、整仓 rsync 或强制覆盖工作区实现“同步”。不能确认文件归属时，提出一个具体问题，并继续不依赖答案的只读检查。

## 4. 安全更新 main 的标准流程

### 4.1 获取远端信息

确认 origin 正确后执行：

```sh
git fetch origin
```

认证或网络失败就报告真实错误，不把 fetch 失败后的旧 origin/main 当最新版本。不要在日志中输出 GitHub token 或配置密钥。

### 4.2 比较本地 main 与 origin/main

本地 main 存在时：

```sh
git rev-list --left-right --count main...origin/main
git log --oneline main..origin/main
git log --oneline origin/main..main
```

第一条结果是 `本地独有提交数 远端独有提交数`：

| 结果 | 判断 | 处理 |
| --- | --- | --- |
| `0 0` | 已同步 | 不制造无意义 merge commit |
| `0 N` | 本地只落后 | 工作区可安全切换时，按下文快进 |
| `N 0` | 本地主分支有未发布提交 | 先登记提交归属并保存在任务分支；不能擅自推 main 或丢弃 |
| `N M` | 两边分叉 | 停止自动 pull，列出双方提交及冲突范围，交主整合窗口决定；不强推或自动 rebase |

本地没有 main 时，先确认工作区可切换，再执行 `git switch --track -c main origin/main`。不要覆盖已存在的同名分支。

### 4.3 快进更新

只有仓库正确、工作区安全且没有本地独有 main 提交时，依次执行：

```sh
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git rev-parse origin/main
git status --short --branch
```

**上一条失败，不执行依赖它的下一条。** 禁止 pull 失败后改用 `reset --hard`、强制 checkout、普通 merge 或 rebase“修好”。如果远端恰好更新导致不能快进，重新 fetch 和比较，不覆盖他人提交。

成功标准：pull 成功，HEAD 与本轮 origin/main 一致，工作区原有资料没有被改写。记录最终 SHA；不要只说“已经最新”。

首次获取项目时，使用正确 origin 的 git clone；同名目录已存在则先核实，不能删除后重克隆。

## 5. 更新自己的模块开发分支

### 新任务

main 更新完成后，从已确认基线建立新分支，命名如：

```sh
git switch -c codex/m04-feat-training-plan
```

例子不是要求所有成员都用 M04；按真实模块/任务命名。只在此分支改分配范围，不在 main 直接写模块功能。

### 已有未完成任务

保留原分支和提交；比较该任务与最新 main 的重叠文件。如果该任务包含“与当前主分支整合”的授权，可在干净任务分支执行：

```sh
git switch 真实任务分支
git merge origin/main
```

上面的“真实任务分支”是占位文字，不能原样执行。若任务只要求拉取 main，报告开发分支的落后/冲突情况，不擅自扩展为合并该任务代码。

冲突按功能组合：M01 身份/客户端/事务/上传/通知、M02 健康档案、M03 营养、M05 积分/预约等已验收能力全部保护。禁止 `--ours` / `--theirs` 整文件采纳，不能因为自己负责某个页面就覆盖该页面其他模块的组件。

未经本轮授权，不改写已经进入审核的提交，不擅自 rebase/force-push。冲突无法确定产品行为时，保留双方实现和现场，报告具体差异；不以“最新版”替代产品决定。

## 6. 依赖与环境配置

更新前后比较 package 文件、锁文件和 scripts。依赖没变且已安装完整时，不为同步而重新安装或升级。

- H5 与当前正式后端使用其提交的 package-lock.json，需要安装时在对应仓库执行 `npm ci`。
- 管理后台当前使用 pnpm-lock.yaml，需要安装时执行 `pnpm install --frozen-lockfile`；不要用 npm install 生成另一套锁。
- 未来锁文件变化时，以该仓 README、packageManager 字段及唯一有效锁文件为准。遇到多个冲突锁文件先报告，不自行删选。
- 安装前读取 package.json 生命周期脚本；网络、镜像、版本不兼容要如实报告，不修改锁文件、降级 Nest/Next 或关闭校验来制造“安装成功”。
- `.env.local` 等本地配置不会随 Git 自动提供。只列缺失的变量名、用途和示例路径，不打印实际值，不复用别人的 SMTP、数据库、模型密钥。
- 当前后端保持统一 Nest/NodeNext/ESM，前端 Next/React 版本以目标仓库为准。写 Next.js 代码前读安装版本的 `node_modules/next/dist/docs/`。

当前默认本地端口：H5 3001、API 3002、后台 3003、MySQL 3307、Redis 6380。尊重个人实际配置。端口占用先识别进程归属，不能 killall node 或停止其他窗口服务；仅拉取代码不代表必须重启服务。

## 7. 后端数据库：先核对，再升级

本版状态：QY-MYSQL-1.1.0 / V006，46 张业务表，另有 schema_migrations。V005 增加运营消息两表及停用的缺失积分规则；V006 仅补旧用户缺失的零余额账户。已有规则、余额和业务记录不覆盖。

### 只核对、不修改

读取 `contracts/schema_manifest.json`、`db/migrations/`、`db/releases/建表与升级说明.md`。核实连接库名/主机及环境归属，不能仅凭“localhost”判断安全，可能是生产隧道。不得输出口令或连接 URL。

允许读取时，用正确连接检查：

```sql
SELECT DATABASE();
SELECT version, sha256 FROM schema_migrations ORDER BY version;
```

`schema_migrations.sha256` 是正式字段，不改为独立包的 checksum_sha256。不修改已应用迁移文件或手工伪造校验记录。

### 需要本地升级时

只有已明确授权配置本地环境、确认库归属、读取脚本和差异后，才在后端仓库执行：

```sh
npm run migrate
```

执行前记录迁移版本和相关业务数量，重要数据先备份。执行后核对历史与校验值、旧数据保留及相关接口。已在 V006 的库通过迁移器进行校验，不再次手工执行 V005/V006 SQL。

遇到校验不一致、手机号旧数据、未知版本、部分 DDL 已执行、权限不足或非本地环境时，停止数据库修改并报告。MySQL DDL 会隐式提交，不能靠 ROLLBACK 撤销建表，更不能删库解决失败。

### 空库和已有库不能混用脚本

- 新建且确认完全为空的库：按发布说明选择 V006 full_install，不能与迁移器初始化再重复安装。
- 已有 V004/V005：用迁移器，或由整合负责人选择对应起点的受保护升级 SQL。
- 已有业务库：**禁止执行 full_install、DROP/reset、演示 seed 或导入成员整库 dump。**
- 数据库升级不自动启用积分、不自动授予管理员、不生成真实权益；这些是独立配置/产品决定。
- 自动化测试仅使用明确隔离、已确认归属的 `_test` 数据库；库名后缀只是必要条件，不能代替环境核实。不要对本人的日常开发记录或线上库运行测试清理脚本。

## 8. 更新后验证：区分“拉取成功”和“能运行”

| 授权任务 | 最低验证 |
| --- | --- |
| 仅拉取/同步 | 三仓需要的版本、HEAD/远端一致、工作区保留、依赖/迁移/配置变化清单 |
| 配置本地环境 | 上述检查 + 授权安装/迁移后的结果 + 实际启动与接口连通 |
| 开发并交付 | 团队规范要求的类型、构建、模块测试及已有能力回归 |

常用检查（先确认当前 scripts 存在）：

```sh
# H5：在前端仓库
npm run typecheck
npm test
npm run build

# 后端：在后端仓库
npm run typecheck
npm run build
# 完整后端测试需要明确的隔离测试库和测试配置，不在此给出可误连日常库的一键命令。

# 后台：按 pnpm 锁安装完成后，在后台仓库
pnpm run typecheck
pnpm test
pnpm run build
```

浏览器和真实外部服务另行验证。编译通过不等于真实邮箱/模型/地图/权益/推送可用；模拟上游和被跳过的 live 测试不能计作真实闭环通过。

必须保留：M01 邮箱与权限、M02 档案/饮水/体重/看板、M03 真实饮食及来源校验、M05 积分/预约/社区/消息/素材、共享账号隔离/事务/幂等/缓存/Worker。

尚缺能力照实呈现：积分规则默认停用；权益供应商、模型/地图、外部推送按配置状态；M04/M06 正式后端尚未整合的部分仍待交付。列表为空不准塞演示内容，测试账号和固定管理员不能接入正式运行。
