# 轻养健康 App｜模块合并统一规范

版本：1.0 · 生效日期：2026-10-20 · 主导：用户负责 M01 和总体整合，本主整合窗口负责执行、协调与验收。

**每个窗口在拉取、适配或合并模块前，必须先读本规范和《模块合并台账》。已经合入并验收的功能默认保留；新包只补齐缺失能力。重复实现先确认采用方案，未确认不得覆盖。**

本规范用于 M01–M06 持续整合。它规定如何合并；台账记录实际合并到哪一步。代码、页面、表结构、工作包、交付者自测分别核实，不能互相代替。

## 1. 每个窗口开始工作的顺序

1. 阅读本文件、同目录《模块合并台账》及该模块最近一份合并记录。
2. 阅读 00 总契约、01 数据库字段字典和本模块工作包；这些原始材料在前端仓库 `项目功能模型项目规范/`。若独立后端 checkout 没有材料，向主整合窗口索取本模块材料和当前契约，不凭记忆补写规则。
3. 在实际目标仓库运行 `git status --short`、`git branch --show-current`、`git rev-parse HEAD`，前后端分别检查；读取当前路由、组件、端口、契约、迁移和相关测试。
4. 用《模块合并记录模板》创建本次记录，填写交付固定 SHA、前后端实际基线、负责窗口、修改白名单、重叠功能与拟执行测试。先形成“功能对照表”，再改代码。
5. 主整合窗口确认本次文件范围及共享装配负责人。授权范围内的新增、适配和测试直接推进；只有未确认的重复替换、业务口径变化等暂停对应部分，不阻断无冲突功能。

旧交付、旧方案中的 commit 仅说明来源，**不是当前目标基线**。每轮基于台账最新已验收版本及实际 HEAD；二者不一致先核实，不把工作区倒回旧版本。读不到规范、缺少关键确认或发现同时修改同一共享文件时，先保留当前实现并报告具体问题。

## 2. 规范维护与窗口分工

| 角色 | 职责与边界 |
| --- | --- |
| 用户 / 项目负责人 | 决定重复功能保留或覆盖、产品规则、供应商、范围和破坏性数据变化；已给出的授权与决定持续有效 |
| 主整合窗口 | 维护本规范和台账；确定当前基线；整理冲突并给出建议；统一公共代码、端口、契约和迁移号；审查并验收前后端配套结果 |
| 模块窗口 | 在约定范围内交付本模块功能、适配器、测试和合并记录；发现重叠先登记；不得自行接管别组业务或宣布全项目完成 |

这是跨窗口协作约定，不是自动文件锁。共享工作区的多个窗口不要同时写入口、Provider、公共客户端、端口注册、Worker、共享类型、依赖锁或迁移。模块窗口可准备局部补丁，由主整合窗口串行装配；也可在主整合窗口明确分配的独立分支/副本开发。

用户授权合入项目，不等于授权删除其他功能、重置数据、覆盖工作区、强推历史或直接发布线上。已有明确授权的常规步骤不重复询问；新增业务冲突单独提交决定。

## 4. 已验收功能如何保护

台账列出当前最低保护集合。**扫描发现已有真实能力或已验收功能但尚未登记时，也先按保护项处理，核实后补台账，不能因“台账没有”就覆盖。**

每轮都要保留：

- 邮箱验证码注册/登录、已有用户复用、Cookie 会话、刷新/退出、认证重试、Origin/CSRF、账号隔离。
- M01 账号资料/头像、私有上传与校验、安全图片、站内通知与已读、媒体和 Outbox Worker。
- M02 真实档案、版本冲突、饮水/体重增删及历史记录、上限并发、删除回退、看板和 7/30 天大屏。
- 统一请求器、缓存失效和账号切换清理；网络丢响应沿用幂等 key，明确业务失败后新提交使用新 key。
- `availability` / `rewardsAvailable`、未知值 null 的语义；新模块只改变自己真正接入的能力标志。
- 已完成迁移、唯一约束、外键、CHECK、锁顺序及同事务业务事实/积分，不用演示状态或弱校验替换。

保护行为不意味着文件永远不能修改。可以增加入口、注入端口、抽取共享组件、做兼容适配；修改后必须证明原行为仍成立。原行为要改变或退出，先进入重复功能/行为变更确认流程。

## 5. 按功能逐项决定如何接入

每个交付功能必须落到以下一种分类；不能仅写“合并 nutrition 文件夹”。

| 分类 | 判断 | 执行规则 |
| --- | --- | --- |
| A 已有真实功能 + 新包相同功能 | 两边操作、API、数据事实相同或覆盖范围相交 | 默认保留当前实现，调用/复用；想替换或双留则登记 DUP 并确认 |
| B 已有部分真实功能 + 新包补足 | 当前有子能力，新包实现尚缺部分 | 逐项补齐；原子能力、数据和入口保留，不能用较旧整页替代 |
| C 已有演示/占位 + 新包真实实现 | 外观看似存在，底层仍为 mock/localStorage | 标出真实替换范围和会消失的演示交互；如已有重复行为或产品取舍，先登记确认，不把 demo 数据导入真实用户 |
| D 当前完全缺失 + 新包已实现 | 没有同职责事实、接口和交互 | 接入真实实现、依赖及测试；无业务冲突无需额外重复确认 |
| E 当前缺失 + 新包仅设计/桩 | 工作包写了，但源码/真实配置未完成 | 记录为待实现/待配置；不能把设计、空端口或 UI 当成已实现 |
| F 同一页面的不同模块能力 | 比如账号、档案、积分共处“我的” | 组合现有组件，只新增所属功能；布局合并不覆盖其他模块 |
| G 公共能力重复 | 新包自带登录、客户端、连接池、事务、上传、通知等 | 复用现有 M01；仅移植业务调用，不接入重复底座。发现实际语义不同则交主整合窗口处理 |

比较对象是“用户操作 + 接口 + 事实数据 + 副作用”，不是函数名。名字不同也可能重复；同名文件也可能需要组合。

## 6. 重复功能必须留下确认记录

在本次合并记录建立 `DUP-M0X-序号`，至少填写：当前实现和路径、交付实现和路径、各自已验收证据、行为/字段/数据差异、影响模块、推荐方案、待决定事项、确认来源、最终选择与回归用例。

允许选择：

1. **保留现有并复用**：新包移除重复入口或改为调用当前能力。
2. **组合补齐**：保留现有能力，仅吸收缺少的部分；明确唯一写入口和唯一数据事实。
3. **确认后替换**：列清旧行为如何迁移、哪些原测试保留、退出条件和回滚方式。
4. **有意双留**：只有用户确认用途确实不同才保留两套入口，明确命名和数据归属；不能产生两份互相矛盾的事实。

**未确认状态一律保留当前实现。** 当前用户已批准的 M02 真实档案和记录整合属于既有决定，不每次重新询问；但新交付想用它自己的档案/饮水/体重替换时，是新的重复决策，不能沿用其他事项的确认。

技术适配、正确性修复和不改变原行为的组件组合，由主整合窗口在既有授权内处理；产品行为变化、替换已测实现、数据迁移/丢弃、积分规则及供应商变化交用户确认。确认不能用“等待一段时间无人回复”或其他窗口自己的建议代替。

## 7. 统一技术与装配要求

- 当前前端 Next.js 16.4.2 / React 19.3.1 / TypeScript，后端 NestJS 12 / TypeScript / MySQL 8.4 / mysql2 / Redis / BullMQ。以目标仓库 package.json 和锁文件为准，不复制交付包较旧版本或批量升级依赖。Next 代码修改先读已安装 `node_modules/next/dist/docs/` 的相关指南。
- 路由统一 `/api/v1`，camelCase JSON、snake_case SQL；复用已有错误信封、HTTP 状态、CSRF、鉴权和重试规则。不能把公共业务错误误报500，也不能泄露未知异常详情。
- 保留 `<FE>/src/components/auth-provider.tsx`、`src/lib/api/client.ts`、`src/lib/api/cache.ts`、API rewrite。业务模块不再创建第二套身份或自行拼装 Cookie。
- 后端在现有入口追加路由/端口；检查原入口的提前404、路由顺序及状态码。保留原鉴权和生产启动检查。NodeNext 导入与双仓库相对路径要适配目标项目。
- `modulePorts` 增量注册，不能把整对象重赋值为新模块默认值，不能清掉其他真实端口。Worker/Outbox 消费者、白名单、恢复任务和关闭流程同样追加装配，保留原媒体/通知消费者。
- 所有查询端口复用传入 tx，不另开连接；同事务写入端口不提前提交、使用外部网络或另起事务。上海业务日与 UTC 存储规则不变。
- 前端刷新连接共享失效边界；日期变更更新新旧日期，账号切换取消/忽略旧请求，不显示前一用户数据。不要为局部功能复制全局 Provider 或演示 reducer。
- `<BE>/contracts/shared_types.ts` 是实施共享类型维护源；同步前端 `contracts/shared_types.ts` 和对应 OpenAPI。旧工作包附录用于对照，不能覆盖已发布的邮箱身份和 M02 nullable/能力字段。

## 8. 缺依赖与演示数据的处理

真实、演示、仅设计、未配置和未测试必须分别列出。测试账号、dev server、伪积分、空 QueryPort、模拟识别结果不得进入正式运行装配。

当前 M02 已确认的兼容策略：其他端口缺失时，自己的健康记录照常保存；对应聚合返回 null 和 availability=false；缺少积分端口时 rewardsAvailable=false，不写积分、不承诺补发。其他新模块不能自动照抄这项例外：如果其契约规定必须发奖或必须真实供应商，先报告依赖，主整合窗口依据确认决定拒绝写入、阶段性禁用或调整契约，并记清验收范围。

真实端口到位后再启用相应能力，验证事实写入、奖励一次、快照查询和刷新一致。不能因接上一个 NutritionQueryPort 就同时把所有 capability 标记为 true。演示训练完成、心情或本地积分不作为真实看板数据。

供应商配置模板存在不等于实际调用可用；本地测试通过不等于线上配置/发布通过。密钥只在对应环境注入，不向浏览器发送或写入交付文档。

## 9. 数据库合并规则

当前已验收契约 QY-MYSQL-1.1.0、Schema V004、44 张业务表；V001 SHA-256：`64ec33a66c813321d12a7bbc29eff4d3981d6d3f3eacf6fc1eb7f9265efd3c56`。这些值是本版快照，之后以台账已发布版本为准。

- 合并业务代码、合法 seed 和迁移，不合并组员本地数据库数据、密码或整库 dump。
- 先比较已有表、字段、索引、约束与目标契约；基线已存在的表不重复创建。模块完成不意味着要再建一套表。
- V001–已应用迁移不可改写；新增结构先提交 CR，由主整合窗口分配下一可用迁移号，不各抢 V005。
- 分别测试空库安装、已有版本升级和已应用迁移重跑检查；MySQL DDL 隐式提交，不能假设回滚事务可撤销建表。
- 不得用 DROP、reset、删除真实记录、禁用约束或导入测试事实解决代码合并冲突。破坏性变化需明确数据方案、备份与用户确认。
- 统一生成并核对 `<BE>/db/releases/` 安装/升级 SQL、校验值及迁移历史；单模块参考 SQL 不能作为对已有库的安装脚本。

## 10. 每次合并的固定流程

### 阶段一：接收、盘点与确认

固定来源仓库/commit，读取脚本后才执行；记录交付校验值、源码基线、真实依赖。扫描当前代码和测试，填写功能对照、文件/表归属、冲突与新增依赖。处理 DUP；未决项只暂停相应替换，不静默选新版本。

### 阶段二：选择性接入

在独立 `codex/integrate-m0x` 分支或批准的隔离副本实施。保留现有页面/组件/入口和已测行为，按确认范围增加功能、适配正式端口。主整合窗口串行修改共享文件；不要整仓 rsync、无关历史整合并、目录整体覆盖或用 ours/theirs 一键解决公共文件。

开始前记录已存在的脏文件；写入前再次确认目标未被其他窗口改变。有新增并发改动时重新比较，不从旧缓存文件回写。不得 reset/clean/stash 未经本任务授权的工作、停止其他窗口的进程或抹除环境配置。

### 阶段三：新功能与已有能力一起验证

运行目标模块测试与所有受影响保护用例。核心行为出错即停止整合，不删除或放宽断言来宣称通过。旧 demo 用例确实因已确认真实替换失效时，要改成对应真实/契约测试并保留原用户行为覆盖，记录原因。

### 阶段四：审查、保存与交接

审查最终差异、文件/表归属、真实/mock清单和未决项。前后端分别提交，**git add 使用明确文件白名单，禁止为省事把整个 docs/integration、scripts 或工作区加入提交**；检查 staged diff 后才 commit，不夹带其他窗口同时创建的文件。

更新本次记录和台账：准确写前后端 SHA、验证环境/命令/结果、剩余能力、数据库变化、回滚及发布状态。两仓配套提交未齐，不声明整合完成。代码合入、远端推送、合入main、部署线上是四种状态，分别记录，不擅自混同。

| 页面 | 手机/桌面无溢出，弹层与导航可用，“我的”保留账号和档案组件；真实与演示状态清晰 |
| 数据库 | 表结构一致、旧数据保留、迁移校验；结构变化须额外测试空库/升级，没DDL则记录无DDL及原因 |
