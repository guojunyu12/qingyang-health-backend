# 轻养健康 App｜团队开发与 Git 提交规范

版本：1.0.0｜生效日期：2026-10-21｜维护者：主整合窗口（用户指定的本窗口）

**适用 M01–M06，以及 H5、后端、管理后台三个仓库。所有成员与 AI 编码助手开始工作和提交 PR 前必须阅读本规范。模块成员交付候选代码，主整合窗口负责后续审查、适配、合并和验收；项目负责人决定产品取舍和破坏性变更。**

## 1. 文件放置与执行入口

每个成员在自己的每个仓库中保存以下文件，提交进 Git，不只保存在编辑器聊天记录里：

| 文件 | 用途 |
| --- | --- |
| `docs/integration/团队开发与Git提交规范.md` | 本文件，开发与提交规则主本的副本 |
| `docs/integration/模块交付与PR说明模板.md` | 每次交付及 PR 的说明模板 |
| `docs/integration/模块合并规范.md` | 现有功能保护、重复实现与合并规则 |
| `docs/integration/模块合并台账.md` | 已验收功能及历史；实际基线仍须向主整合窗口核实 |
| 根目录 `AGENTS.md` | 添加同目录《编辑器规则接入说明.md》中的入口段落 |

Codex 使用 AGENTS.md；其他编辑器按《编辑器规则接入说明》引用这些文件。保留原有规则，不能用本段覆盖整个 AGENTS.md。独立后台仓库也必须有入口。不同机器使用仓库相对路径，不复制主导者电脑的绝对路径。

本规范由主整合窗口维护，前端 `docs/integration/` 为维护主本；后端、管理后台保存同版本副本。成员可以提出规则变更，但不能自行发布不同版本或删除规则绕过审核。业务产品与数据库契约仍以已确认的最新版本为准；发生冲突，保留当前功能，向主整合窗口登记具体差异，不自行猜测。

| 仓库 | 范围 |

| `guojunyu12/qingyang-health-frontend` | 用户 H5 前端 |

## 3. 代码格式与命名

这些是新增、实质修改代码的统一写法，不要求为了格式重写整个旧文件。

| 项目 | 约定 |
| --- | --- |
| 文本 | UTF-8、LF 换行、文件末尾一个换行、清理行尾空格 |
| TS/TSX/JS/JSON/CSS | 缩进 2 个空格，不用 Tab；TS/JS 使用分号、双引号；多行结构保留工具支持的尾逗号 |
| 行长 | 以 100 字符为格式化目标；长 URL、不可拆字符串可例外；禁止把整段业务压成一行 |
| 格式工具 | 已有格式工具沿用配置；没有时按本表编写，由主整合窗口集中落地统一配置。禁止各成员自行引入冲突的 formatter 或全仓格式化 |
| 文件/目录 | 新业务文件采用 kebab-case，如 `points-service.ts`；已有模块的 service.ts 等结构保持一致 |
| 标识符 | 组件/类/类型 PascalCase，函数/变量 camelCase，真正常量 UPPER_SNAKE_CASE，React Hook 以 use 开头 |
| 字段 | HTTP JSON camelCase；SQL 表/列 snake_case；边界显式映射，不整仓改名 |
| 类型 | 导出 API/Port/DTO 明确输入与返回类型；使用 type-only import；禁止用 any、非空断言或 ts-ignore 掩盖契约错误。必要例外注明原因与约束 |
| 注释 | 解释业务规则、并发、权限和取舍；避免逐行复述代码。临时事项写 `TODO(M05): 说明及追踪链接`，不能用 TODO 冒充完成 |
| 模块 | UI、API 请求、业务规则、数据访问分开；SQL 不写在页面组件里；组件不拼接私有 Cookie，不包含服务端密钥 |
| 错误 | 明确处理加载、空数据、未配置、权限、版本冲突和失败恢复；禁止 catch 后伪造成功或返回演示数据 |

Python/SQL/Shell 等保留所属仓库已经使用的标准格式；Python 4 空格，SQL 语句清晰分行。不要把 TS 的 2 空格规则套用到 Python。

只格式化本次变更涉及的代码，不夹带无关改名、移动、排序或版本升级。确需大规模纯格式变更时，单独提交、单独审核，避开其他模块并行修改。

## 4. 技术与接口统一要求

1. 以指定基线的 package.json、锁文件和配置为准。当前整合前端为 Next 16/React 19，后端 Nest 12、NodeNext/ESM、MySQL、Redis/BullMQ；不得从独立包带回旧 Nest/CommonJS 或整份覆盖依赖文件。
2. Next.js 修改前阅读当前安装版本 `node_modules/next/dist/docs/` 的相关文档。服务端 NodeNext 导入遵循现有文件扩展名约定。
3. 复用 M01 邮箱登录、会话、Origin/CSRF、用户/管理员权限、公共请求器、上传和通知。禁止把固定测试账号、dev 身份或第二套会话接到正式业务中。
4. 使用统一 `/api/v1` 和已有响应/错误信封。不得新增接管全部 `/api/**` 的模块代理，也不能覆盖现有 rewrite。独立模块联调代理只能限定自己的明确路径，整合时按正式入口适配。
5. 跨模块调用正式 Port，查询复用只读快照，同事务写入复用 SqlTx。不能另开事务导致事实已保存、积分失败，或绕过所属模块直接改其表。
6. 公共入口、Provider、认证、请求器、共享契约、端口注册、Worker、依赖锁和迁移由主整合窗口统一装配。成员在交付单中列出所需变更；必要代码可提交为明确标注的候选，不能未经分配修改公共行为。
7. Outbox 由唯一统一分发链路管理，新增消费者接入现有队列；不得另建争抢相同 outbox_events 状态的轮询器。注册新能力不能清空既有消费者或 modulePorts。
8. API 变化同步 DTO、共享类型、OpenAPI 和前端调用。新增/删字段、nullable、枚举、分页、时区、金额/积分单位、幂等规则和错误码必须写入交付单。破坏性变更先评审兼容策略。
9. 保留 AccountSummary、HealthProfilePanel、站内通知、退出登录等已有能力。共享页面采用组件组合，不整页回填旧包。
10. 真实、演示、未配置、未测试分别标明；无供应商配置不得退回伪成功。密钥不进浏览器、Git、截图、日志、PR 和交付文档。公开仓库尤其不得提交真实邮箱授权码、数据库口令或用户数据。

## 5. 数据库交付

当前规则快照为契约 QY-MYSQL-1.1.0 / V004，后续以主整合窗口发布的新版本为准。成员不能依据旧 V001 包另建一套正式库。

- 已应用迁移不可修改或重命名，不改 V001 校验值，不重复创建已有表。
- 结构变更先交数据库 CR：所属模块、现状、拟变更 SQL、用途、索引/外键/CHECK、数据兼容、锁表影响、预计数据量、发布顺序、恢复方案。
- 未获迁移号时使用 `db/proposals/CR-M05-001.sql` 等候选名；由主整合窗口分配正式 V 编号并接入现有迁移器。不能各自创建 V005。
- 复用 `schema_migrations` 的现有字段和校验语义，不另建 `checksum_sha256` 历史列替代当前 `sha256`。
- 测试分为空库安装、现有版本升级、重复执行检查、约束验证及旧数据保留；测试只能连接明确隔离的 `_test` 库。禁止安装/种子脚本默认覆盖现有开发或生产库。
- MySQL DDL 会隐式提交，说明失败在半途如何恢复；不得笼统写“事务回滚建表”。
- seed 与迁移分开，演示账号和业务事实不能导入正式用户库。没有 DDL 也必须明确填写“无结构变化”。
- 提交候选 SQL 和使用说明；统一发布安装/升级 SQL 由主整合窗口生成及复核。Git 回滚不等于数据库回滚。

## 6. 分支与工作节奏

分支名：`codex/<模块>-<类型>-<短主题>`，例如 `codex/m05-feat-booking-cancel`、`codex/m03-fix-camera-cleanup`。整合分支由主整合窗口管理。每个分支围绕一个可验收目标，不用同一分支长期混合多个模块。

固定顺序：

1. 主整合窗口确认任务、基线、文件范围、共享依赖与验收点。
2. 成员拉取确认的远端分支，从指定 SHA 创建任务分支，记录起点。
3. 实现一个完整切片，完成对应测试和文档；一个用户行为需要前后端配套时同步交付。
4. 推送任务分支，尽早创建 Draft PR；未完成项放入待办，不用正式 Ready PR 隐藏依赖。
5. 完成交付模板和测试证据后转为可审查；主整合窗口审核并分配整改。
6. 整改追加提交，说明对应审查编号；完成后由主整合窗口选择性整合、回归、更新台账，再合入指定目标。

模块成员不自行合 main、发布生产、强推共享分支或改写别人提交。默认不 rebase/force-push 已进入审核的分支；确需重写时先与主整合窗口协调，保留旧 SHA 与变更对照。个人分支同步目标分支也要确认目标正确，不盲目 merge 旧 main。

无需为了固定频率制造空提交。每完成一个可解释、可回滚、可测试的切片再提交；工作中断可推 Draft/WIP 分支备份，但交付前整理为能审查的提交，不把 WIP 当完成记录。

## 7. Commit 信息及提交内容

格式：`<type>(<scope>): <做了什么>`。type 使用 feat、fix、refactor、test、docs、chore、build、ci、perf、style、revert；scope 使用 m01–m06、admin、shared、db、integration。标题用简洁中文或英文，建议不超过 72 字符，不写“更新代码”“最终版”“改了一下”。

例：

```text
fix(m05): 取消预约时释放名额并防止重复退款

原因：取消请求重试会重复返还积分。
修改：复用统一事务及幂等请求，退款流水使用唯一事件键。
验证：取消、重复请求、跨账号及事务失败用例通过。
关联：M05-BOOKING-003；backend#12；frontend#9
```

- 一个提交只表达一项逻辑目的，可包含实现与对应测试/文档。多项独立功能拆开；禁止每个文件机械拆成一个提交。
- 重构/纯格式/依赖升级与业务修改分离。依赖调整提交 package 文件和唯一适用的锁文件，不混用 npm/pnpm/yarn 生成多套锁。
- 提交前 `git diff`，明确文件白名单 `git add <文件…>`，检查 `git diff --cached` 和 `git diff --cached --check`。禁止为省事 `git add .` / `git add -A` 把其他窗口或本地资料混入。
- 禁止提交 node_modules、构建目录、缓存、测试库、整库 dump、真实用户数据及密钥。配置示例只含占位符；如仓库忽略 `.env*`，由主整合窗口明确放行示例，不能强行加入真实配置。
- 三个仓库分别提交、分别记录 SHA。前端推送不代表后端交付，后端通过不代表后台可用。
- 修复审查项时写明 `F1`/`F2` 等来源及补测，不能只回复“已修复”。交付后新的提交必须更新 PR 的验证范围。

## 8. PR 与跨仓库配套说明

PR 标题使用相同 type(scope) 格式，目标选择主整合窗口指定分支。正文使用《模块交付与PR说明模板》，不能只贴截图或写“功能完成”。至少包含：

- 问题和最终行为、明确功能清单、未实现/未配置/演示范围。
- 起始 SHA、目标分支、当前交付 SHA、关联三个仓库的 PR/commit；未涉及仓库写“不涉及”。
- 影响文件、公共装配和已有功能保护；重复功能的保留/组合/待确认方案。
- 接口/契约/数据库/依赖/配置变化；无变化明确写无。
- 可复现的环境、命令、真实结果、跳过项、供应商替身范围；UI 变化附脱敏截图或录屏。
- 发布前置条件、后端/前端上线顺序、回滚与数据影响。
- 对应审查整改列表和仍未解决的风险。

交付 SHA 在提交产生后填写 PR 或外部配对清单，不要求某个 commit 的文件包含该 commit 自身的 SHA。共享交付编号例如 `QY-M05-20261021-01`，三个仓库沿用同编号。PR 相互链接；一端未到位时标明阻塞，不宣称完成。

旧 PR 对旧 main 的差异不构成整合证据。先由主整合窗口决定转目标分支、重新基于当前版本移植或选择性接入；禁止为消除冲突整仓覆盖、直接选择 theirs/ours 或回退项目基线。

## 9. 测试与审核门槛

| 范围 | 必须交付的验证 |
| --- | --- |
| H5/后台 | 锁文件环境类型检查、生产构建、变更流程；手机布局、空态、失败态、权限、账号切换；当前脚本以 package.json 为准 |
| 后端 | 类型检查、构建、实际模块测试；输入、认证/CSRF、跨账号、幂等、并发、事务失败和恢复 |
| 共享装配 | 回归登录/刷新/退出、上传/通知、已有 M02/M03 受影响流程，验证旧路由及端口未被替换 |
| 跨模块 | 真实业务事实→Port→积分/通知/看板→页面刷新，适用时验证同事务和一次性处理 |
| 数据库 | 本规范第 5 节的安装/升级/重跑/约束及保留旧数据检查 |
| 外部能力 | 区分真实供应商测试、确定性替身、仅配置；不以 mock 通过冒充线上可用 |

命令必须来自实际项目，不能为交付临时写一个总是成功的 test 脚本。失败、跳过和未执行都如实说明；测试环境不可用时交付“候选，待验证”，不能标“验收通过”。不删除旧测试、不放宽关键断言掩盖回归。

审核：P0 为数据破坏/凭证暴露等严重问题；P1 为核心功能、安全或整合阻塞；P2 为需处理的一般缺陷；P3 为非阻塞建议。P0/P1 未解决不得整合发布；P2 是否阻塞由主整合窗口依据影响记录决定；P3 可后续跟踪。批准只针对固定 SHA，新提交导致结论失效时需重新复核。

本文规定的是团队流程；**尚未声称 GitHub 分支保护、CI、格式化检查或 CODEOWNERS 已自动配置。** 未配置期间人工执行同样门槛，自动化由主整合窗口后续集中落地。

## 10. 主整合窗口的操作边界

主整合窗口负责固定交付版本、核实功能差异、解决技术装配、分配迁移号、维护契约、执行保护回归并记录结果。接收功能不代表接受来稿独立底座；优先复用已验收实现。

重复业务保留/覆盖、积分产品规则、供应商选择及破坏性数据迁移交项目负责人决定。常规兼容适配与正确性整改在既有授权内推进，不把每个实现细节变成等待确认。

状态统一为：开发中 → 已推送候选 → 待审核 → 整改中 → 待整合验收 → 已整合验收 → 已合目标分支 → 已部署 → 线上验收通过。没有达到的状态不得提前写入；“已推 GitHub”不等于“已合并”，“前端上线”不等于“后端可用”。

后续每轮合并先读本规范、《模块合并规范》和最新台账，再固定实际 SHA；保留历史验收与当前未提交工作。只撤销本轮有范围的变更，不能为回滚 M05 删除之后其他模块的代码。
